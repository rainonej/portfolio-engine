# 1. Patch: label taxonomy and issue-routing system

## Why this patch is needed

The original v1 roadmap had an epic for standardizing labels. That was partially dropped in v4.

The current repo docs also still define `claude-ready` as a Claude-specific approval gate. That does not fit the new direction because the workflow-kit is provider-neutral Python/MCP tooling and should support Claude, Copilot, and future agents.

## New decision

Deprecate:

```text
claude-ready
```

Replace with:

```text
agent:approved
```

or, if the repo prefers automation terminology:

```text
automation:approved
```

Recommendation: use `agent:approved`.

Why:

- It is provider-neutral.
- It can apply to Claude, Copilot, OpenHands, Aider, or future tools.
- It separates the approval concept from the executor identity.

## Updated label groups

### Source labels

Keep:

```text
source:human
source:vercel
source:cms
```

Add:

```text
source:workflow-kit
source:agent
source:downstream
```

Meanings:

| Label | Meaning |
|---|---|
| `source:workflow-kit` | Issue body generated by portfolio-engine workflow-kit MCP tool |
| `source:agent` | Created by an AI agent outside a formal workflow-kit tool |
| `source:downstream` | Originated from a downstream consumer repo request or patch |

Use exactly one `source:*` label where practical.

### Task-kind labels

Keep:

```text
type:epic
task:feat
task:bug-fix
task:chore
task:decision
task:content
```

Add:

```text
task:research
task:design
task:docs
task:migration
task:release
```

Notes:

- `task:docs` is more precise than treating all docs work as `task:chore`.
- `task:migration` is useful for config path/layout changes.
- `task:release` is useful for Changesets/npm/PyPI/Vercel release flows.

### Owner labels

Keep the “exactly one owner label per task” rule.

Keep:

```text
owner:simple-ai
owner:agentic-ai
owner:human-dev
owner:site-owner
```

Clarify:

| Label | Meaning |
|---|---|
| `owner:simple-ai` | Mechanical, well-scoped change; can be done by Copilot/coding agent with little reasoning |
| `owner:agentic-ai` | Multi-file or reasoning-heavy change; safe only after `agent:approved` |
| `owner:human-dev` | Requires architecture decision, credential, UI dashboard, merge approval, or personal judgment |
| `owner:site-owner` | Requires consumer/site owner content, brand, or design approval |

### Agent/automation state labels

Replace Claude-specific gate with provider-neutral labels.

Use:

```text
agent:approved
agent:needs-human-review
agent:blocked
```

Keep or refine:

```text
automation:plan
automation:planned
automation:started
```

Possible final set:

| Label | Meaning |
|---|---|
| `agent:approved` | Human approved an AI agent to act on this issue |
| `agent:needs-human-review` | Agent may plan/summarize but should not implement |
| `agent:blocked` | Agent cannot continue without human input |
| `automation:plan` | Human requested issue-shaping/planning workflow |
| `automation:planned` | Planning workflow completed |
| `automation:started` | Execution workflow started |

### Area labels

The old area set was too small. Standardize this as the primary package/domain axis.

Recommended area labels:

```text
area:schema
area:engine-core
area:editorial-theme
area:admin-tools
area:workflow-kit
area:demo-site
area:consumer-layout
area:consumer-registry
area:docs
area:governance
area:safety
area:ci
area:release
area:downstream
area:vercel
```

Rules:

- Each task should usually have exactly one primary `area:*` label.
- Epics may carry multiple `area:*` labels if genuinely cross-cutting.
- Prefer package names where possible:
  - `area:editorial-theme`, not just `area:theme`
  - `area:engine-core`, not generic `area:runtime`

### MVP and roadmap labels

Optional but useful:

```text
mvp:required
mvp:post
mvp:optional
```

Meaning:

| Label | Meaning |
|---|---|
| `mvp:required` | Needed before stable backbone MVP |
| `mvp:post` | Known post-MVP enhancement |
| `mvp:optional` | Optional product expansion, not needed for backbone |

### Lifecycle labels

Add:

```text
lifecycle:blocked
lifecycle:breaking-change
lifecycle:migration
lifecycle:deferred
lifecycle:ready-for-review
lifecycle:needs-decision
```

Do not overuse. Use only when it helps project board views.

# 2. Patch: explicit default registries in runtime packages

## Why this patch is needed

The v4 report discusses runtime registries, but it should more clearly state that the upstream packages should ship **default registries**.

This is important because:

- consumer agents need to navigate upstream source easily;
- future consumer registry support should mirror the default registry system;
- admin-tools and workflow-kit need machine-readable capabilities;
- the project should feel like “registry-first” architecture, not scattered hardcoded route/component lists.

## New target structure

Add registry folders to runtime packages.

### `packages/schema/src/registry/`

Purpose:

- Type/schema definitions for registry entries.
- Shared contracts used by engine-core, editorial-theme, admin-tools, workflow-kit.

Target:

```text
packages/schema/src/
  registry/
    routes.ts
    override-surfaces.ts
    embed-services.ts
    consumer-extensions.ts
    manifest.ts
```

### `packages/engine-core/src/registry/`

Purpose:

- Generic registry merging/validation/runtime utilities.
- Does not own editorial-theme defaults.

Target:

```text
packages/engine-core/src/
  registry/
    normalize.ts
    validate.ts
    merge.ts
    manifest.ts
```

### `packages/editorial-theme/src/registry/`

Purpose:

- The default routes/pages/components/services shipped by the theme.

Target:

```text
packages/editorial-theme/src/
  registry/
    routes.ts
    pages.ts
    components.ts
    override-surfaces.ts
    embed-services.ts
    default-config.ts
```

Examples of default registry entries:

```text
routes:
  /
  /about
  /contact
  /work
  /work/[slug]
  /writing
  /writing/[slug]

override-surfaces:
  Hero
  FeaturedWriting
  TestimonialSection
  CollaborationSection

embed/services:
  basic external link
  calendar/booking link or embed, if supported
  image/media reference
  maybe iframe/embed service later
```

## Important architecture rule

Keep dependency direction:

```text
schema
  ↓
engine-core
  ↓
editorial-theme
```

So:

- `schema` defines types;
- `engine-core` defines generic registry behavior;
- `editorial-theme` provides default registry values.

Do **not** make `engine-core` import `editorial-theme`.

## New/updated epic to add

```markdown

## Labels

type:epic
area:schema
area:engine-core
area:editorial-theme
source:human

## Why

The runtime packages should expose default routes, pages, override surfaces, and services as explicit registries. This makes the engine easier for humans, agents, admin-tools, and workflow-kit to inspect.

## Acceptance criteria

- [ ] Registry types live in schema.
- [ ] Generic registry utilities live in engine-core.
- [ ] Editorial-theme default route/component/override registries exist.
- [ ] Manifest generation reads from registries.
- [ ] Dependency direction remains schema → engine-core → editorial-theme.
```

# 3. Patch: move the ★ MVP marker after consumer layout stabilization

## Why this patch is needed

The v4 report says the MVP is Phase 1 after schema + engine-core + editorial-theme + demo-site + CI + docs + basic overrides.

But the consumer repo layout is foundational. It would be bad to build `agreni-site` and `jordan-site` against the old layout, only to refactor them immediately.

## New MVP definition

MVP should be after:

```text
Phase 1: Runtime package reliability
+
Phase 2: Consumer layout contract
+
demo-site migrated to new layout
+
basic override bridge working
+
README/CONTRIBUTING updated
```

New ★ MVP marker:

```text
schema + engine-core + editorial-theme
+ src/config/src/content/src/context/public layout
+ demo-site using that layout
+ basic named overrides
+ CI/build/deploy docs
= ★ MVP stable backbone
```

## What remains post-MVP

Still post-MVP:

- consumer-owned registry;
- local component embeds;
- Python/MCP workflow-kit;
- admin-tools UI;
- automatic setup script;
- advanced Vercel publishing automation.

## Roadmap patch

Update phases:

```text
Phase 0 — Governance/legal/label foundation
Phase 1 — Runtime package reliability
Phase 2 — Consumer layout contract and demo-site migration
★ MVP stable backbone
Phase 3 — Explicit registries and manifest
Phase 4 — Consumer extension registry
Phase 5 — Python/MCP workflow-kit
Phase 6 — Admin-tools UI
Phase 7 — Setup/bootstrap automation
Phase 8 — Demo/product showcase
Phase 9 — Advanced publishing/preview workflows
```

Note:

- Phase 0 can happen anytime.
- MVP requires Phase 1 + Phase 2.
- Explicit default registries may begin before MVP if needed, but full manifest/consumer extension support is post-MVP.

# 4. Patch: future setup/bootstrap script epic

## Why this patch is needed

Because the target system spans Node/pnpm/Astro plus optional Python/MCP, a nontechnical consumer should not be asked to manually wire every file.

There should eventually be a setup script that bootstraps a consumer repo.

## Setup script target

Possible files:

```text
scripts/setup-consumer.sh
packages/workflow-kit/tools/init_consumer_repo.py
templates/consumer/
```

Possible public instructions:

```text
Create a new repo.
Download setup-consumer.sh.
Run it from your repo root.
Follow the prompts.
```

## What setup should do

### Required runtime setup

- create `package.json` if missing;
- install `astro` and `@portfolio-engine/editorial-theme`;
- create `astro.config.mjs`;
- create `tsconfig.json`;
- create `src/config`, `src/content`, `src/context`, `src/overrides`;
- create `public/media`;
- add README files;
- add placeholder/example JSON/content files;
- create `.gitignore`.

### Optional MCP setup

- install or document Python workflow-kit;
- create `.mcp.json` if the user opts in;
- create or patch `AGENTS.md`;
- explain Claude/Copilot MCP setup.

### Optional Git/Vercel setup guidance

The script should not assume it can complete all dashboard steps.

It should print human steps for:

- creating/connecting GitHub repo;
- connecting Vercel;
- choosing production branch;
- choosing preview branch;
- configuring domain;
- configuring environment/secrets if needed.

## New epic to add

```markdown
# Epic: Consumer bootstrap/setup script

## Labels

type:epic
area:downstream
area:workflow-kit
area:docs
source:human

## Why

Nontechnical users should not manually wire a multi-language project. A setup script should create the consumer repo structure, install runtime packages, and optionally configure AI/MCP instructions.

## MVP relevance

Post-MVP. Helpful for adoption, not required for the stable backbone.

## Acceptance criteria

- [ ] Dry-run mode exists.
- [ ] Existing files are not overwritten without explicit confirmation.
- [ ] Required runtime files are generated.
- [ ] Optional `.mcp.json` can be generated.
- [ ] `AGENTS.md` can be created or patched safely.
- [ ] Human dashboard steps are printed clearly.
```

# 5. Patch: demo-site as product showcase

## Why this patch is needed

The v4 report mentions demo-site as reference and showcase, but this deserves its own future-facing epic.

Demo-site has two roles:

1. **MVP checker** — proves the runtime did not break.
2. **Product showcase** — teaches consumers how to use every layer.

These should be staged separately.

## New split

### MVP role

Demo-site must:

- build;
- run Astro check;
- prove theme integration;
- use target consumer layout;
- deploy on Vercel.

### Post-MVP showcase role

Demo-site should later become an explorable product demo:

- “How config works” page;
- “How content works” page;
- “How context works” page;
- “How public assets work” page;
- “How overrides work” page;
- “How registry works” page;
- “How MCP workflow-kit helps” page;
- rendered result + source snippet side by side.

## New epic to add or expand

```markdown
# Epic: Demo-site as product showcase and living documentation

## Labels

type:epic
area:demo-site
area:docs
source:human

## Why

Demo-site should not only test the runtime. It should also teach nontechnical consumers and agents how to use portfolio-engine.

## MVP relevance

Split into two stages:

- MVP: build/check/deploy reference consumer.
- Post-MVP: full rendered showcase/documentation.

## Acceptance criteria

- [ ] Demo-site remains a reliable CI/build checker.
- [ ] Demo-site uses target consumer layout.
- [ ] Showcase pages explain each layer.
- [ ] Each showcase page links rendered output to source files.
- [ ] MCP/workflow-kit demo is included once workflow-kit exists.
```

# 6. Patch: future admin-tools features and publishing controls

## Why this patch is needed

The v4 report includes admin-tools, but it does not capture several future ideas:

- preview link reveal;
- public vs preview sites;
- dev/main branch promotion;
- weekly publishing;
- nontechnical settings for publishing cadence;
- Vercel/domain guidance.

These are not near-term MVP features, but they clarify where admin-tools is going.

## Admin-tools future modules

### Site overview

- site title;
- current public URL;
- preview URL;
- build/deploy status;
- package versions.

### Content editor

- profile;
- CV;
- writing;
- projects;
- testimonials;
- assets.

### Brand/context editor

- site owner;
- brand voice;
- audience;
- goals;
- tone settings.

### Theme/config editor

- colors;
- fonts;
- navigation;
- features;
- booking/contact links.

### Registry/extensions viewer

- local pages;
- local embeds;
- local components;
- unsupported upstream requests.

### Preview/public publishing panel

Possible features:

- show public production site URL;
- show dev/preview site URL;
- reveal obfuscated Vercel preview link;
- explain who can access preview site;
- show branch mapping:
  - `main` → public production;
  - `dev` → preview;
- create instructions for Vercel project setup;
- optionally trigger or guide dev→main promotion.

### Publishing cadence

Future settings:

```json
{
  "publishing": {
    "mode": "manual",
    "previewBranch": "dev",
    "productionBranch": "main",
    "weeklyPromotion": {
      "enabled": false,
      "day": "Friday",
      "requiresApproval": true
    }
  }
}
```

Possible workflows:

- manual PR from `dev` to `main`;
- scheduled weekly PR;
- scheduled auto-merge only after site-owner approval;
- never auto-publish without explicit opt-in.

## New epic to add

```markdown
## Acceptance criteria

- [ ] Admin UI can display public and preview site concepts.
- [ ] Docs explain dev/main branch model.
- [ ] Vercel setup guidance is available.
```
